# Code Review — Production Gaps

Mismatches between the docs (00–06) and the code at `7be66ec`, plus problems likely to show up in
production. Open GitHub issues (GH #2–#8, #12, #13) are left out. ✔ marks findings reproduced with
a throwaway local Spark test.

| No. | Name | Description | Severity | Resolution |
|---|---|---|---|---|
| ~~1~~ | ~~Silver→Gold and Gold→Export streams fail after first MERGE ✔~~ | ~~APPEND, FULL and UPSERT (and SCD2 by default) stream a delta origin by checkpoint, and `ignoreDeletes` does not cover updates. Every SCD2, COMPLETE_DELTA, UPSERT or FULL target gets MERGEd or overwritten, so the next read fails with `DELTA_SOURCE_TABLE_IGNORE_CHANGES`. The documented Silver→Gold UPSERT and Gold→Export FULL cannot run past their first load.~~ | ~~Severe~~ | Moved to [GH #21](https://github.com/Escoto/EscotoDataFramework/issues/21) |
| 2 | SCD2 commits the close before an insert that can fail ✔ | Closing superseded rows (and COMPLETE_DELTA's full-scope expiry) commits before the insert. If the insert fails every time (a new column under the default `fail_on_new_columns`, or type drift), those keys have no current row. Under COMPLETE_DELTA `snapshot_scope: full` the whole table has none, and retries fail the same way. | High |
| ~~3~~ | ~~Duplicate keys in one batch open duplicate current rows ✔~~ | ~~SCD2 and COMPLETE_DELTA assume one row per key per batch, but dedup is optional and off by default. A new key arriving twice is inserted twice as current; an existing key fails the close MERGE instead.~~ | ~~High~~ | Dedup based on keys by default |
| 4 | NULL or unparseable event time silently corrupts history ✔ | `as_timestamp` returns NULL for a missing value or a format mismatch, and nothing rejects it. SCD2 then skips both the anti-filter and the close and opens a second current row. UPSERT skips the update and dedup keeps an arbitrary row. | High |
| 5 | COMPLETE_DELTA `snapshot_scope: full` writes overlapping validity windows ✔ | Expiry sets `__END_DATE` to the run time, while the re-asserted row reopens at its original event time. Every unchanged record gets overlapping windows, and a replayed backlog records deletions at the run time rather than the snapshot's. As-of queries return several rows per key. | High |
| ~~6~~ | ~~SCD2 full scope merges a backlog as one snapshot ✔~~ | ~~SCD2 treats each micro-batch as one snapshot. When two full exports arrive together, a record the newer one dropped stays current. A late, older export expires everything and brings back its stale rows.~~ | ~~High~~ | Fixed in [GH #22](https://github.com/Escoto/EscotoDataFramework/issues/22): SCD2 no longer accepts `snapshot_scope: full`; it takes changes only |
| 7 | ISO-named or unstamped files never reach Silver ✔ | Provenance parses `__EXPORT_DATE` only from 14 consecutive digits, so ISO names (`snapshot_time_pattern: timestamp`) and unstamped files get NULL. The watermark drops those rows before the `SnapshotPatternError` guard sees them, so the run succeeds and Silver stays empty. The ISO unit test builds `__EXPORT_DATE` by hand, so it never exercises this path. | High |
| 8 | Watermark silently skips late and out-of-order exports | The watermark reads only `__EXPORT_DATE > max(target)`. A late delivery, the second part of a split snapshot, or a feed that lags another feed into the same Silver (the JSON full+delta shape) is never promoted, and nothing is logged. | High |
| 9 | Crash between a snapshot's updates and deletes loses the deletes ✔ | Updates and deletes commit separately per snapshot. Once the updates land, the watermark is past that snapshot, so a retry never re-reads its deletes and the entities stay live. | High |
| 10 | `increment_anchor` corrupts full-scope history ✔ | `increment_anchor` with COMPLETE_DELTA `snapshot_scope: full` reads only changed rows, then expires every unchanged record. The option is undocumented. (`latest_snapshot` was removed in [GH #22](https://github.com/Escoto/EscotoDataFramework/issues/22).) | High |
| ~~11~~ | ~~FULL overwrites with the increment, not the dataset~~ | ~~FULL runs under the checkpoint strategy, so it writes only what arrived since the last run. Two full drops pending together land as their union, with every record twice. A delta source gets only the newly appended rows.~~ | ~~High~~ | Fixed in [GH #22](https://github.com/Escoto/EscotoDataFramework/issues/22): FULL writes only the batch's newest export and skips one older than the target's |
| 12 | Column sanitization misses Delta-invalid characters ✔ | Only space and `,;./` are replaced, so `(){}=`, tab and newline pass through and Delta rejects the write (`Weight (kg)` → `WEIGHT_(KG)`). Headers that collide once uppercased (`Id`, `ID`) fail too. | Mid |
| 13 | Default `multiline: true` reads one row per JSON Lines file ✔ | The framework flips Spark's JSON default to multi-line. A JSON Lines export then silently yields only its first record. | Mid |
| 14 | `add_new_columns` fails every run that meets a new column | Auto Loader deliberately stops the stream when it adds a column and expects a restart. Neither the framework nor the workflow YAML retries, and the docs only say the target grows. | Mid |
| 15 | Cast config is validated per batch, not at Start | The cast YAML is read inside `prepare()`, so a bad path, unknown key or invalid type fails only after data is read, and an idle run never checks it. The DQX ruleset, by contrast, is validated at Start. | Mid |
| 16 | COMPLETE_DELTA recomputes the whole backlog for every snapshot | The increment is never persisted, and `_at()` filters on a derived column that data skipping can't use. Each snapshot re-scans and re-casts the full backlog several times, so cost grows with the square of the backlog. This is separate from GH #3. | Mid |
| ~~17~~ | ~~COMPLETE_DELTA dataset-level checks span every pending snapshot~~ | ~~The gate judges the whole multi-snapshot increment, while the merge runs per snapshot. `is_unique(ID)` therefore fails on every normal backlog, since each snapshot re-sends the same keys.~~ | ~~Mid~~ | Moved to [GH #2](https://github.com/Escoto/EscotoDataFramework/issues/2) |
| 18 | Fan-in tasks share one checkpoint and schema location | Both paths are derived from the target table only. Two tasks writing one target (e.g. two inbound folders into one Bronze table) share streaming offsets and the inferred schema. | Mid |
| 19 | `__SILVER_LAST_MODIFIED_DT` misses closes, expiries and delete flags | The docs define it as the last framework write to touch the row, but the close, full-scope expiry and delete-flag merge don't update it. Incremental readers keyed on it miss those changes. | Mid |
| 20 | Options irrelevant to the verb pass as silent no-ops | `output.dedup.*`, `output.keys` and `output.event_time` on APPEND/FULL, CSV options on JSON (even `escape`, which the docs say applies) and `snapshot_time_pattern` on SCD2 all validate and do nothing. The loader already refuses this pattern for `envelope_fields`. | Mid |
| 21 | Documented table tagging is never invoked | `apply_tags` has no caller and no config key. It also returns silently when the table is missing, where the docs promise a warning. | Mid |
| 22 | KPI names in docs differ from what writers emit | The docs promise `bronze_new_records` / `silver_new_records` for APPEND, but it emits `rows_appended`; FULL and UPSERT emit `rows_overwritten` and `rows_upserted`. The constants in `kpi.py` are unused. | Mid |
| 23 | `flatten_nested` and JSON schema logging are untracked P6 gaps | `flatten_nested` is registered, passes Start validation, then raises `NotImplementedError`. The JSON tree-schema logging from the roadmap doesn't exist, and neither gap has an issue. | Mid |
| 24 | Config validation failures leave no audit row | `load_config` and `build_context` raise before the logger exists. A misconfigured run therefore leaves nothing in the audit table, although the README says every run writes to it. | Mid |
| 25 | Inbound glob misses uppercase extensions and subfolders | `*.csv` is case-sensitive and flat, so `.CSV` files and dated subfolders are skipped. The run still succeeds with nothing ingested. | Low |
| 26 | Deletes feed bypasses prepare, policies and dedup | Deletes are read raw, so rename patterns and casts never reach their keys and no check runs. A key deleted twice in one snapshot fails the MERGE. | Low |
| 27 | Delete-then-recreate in one snapshot ends deleted | Deletes apply after the snapshot's updates, whatever the event times. An entity deleted and then re-created in one export ends flagged deleted, with `__END_DATE` before `__START_DATE`. | Low |
| ~~28~~ | ~~Audit table creation races; `name` partitioning fragments it~~ | ~~`CREATE TABLE` has no `IF NOT EXISTS`, so parallel first runs in a new env can fail. Partitioning by the high-cardinality `name` column builds up small files.~~ | ~~Low~~ | Moved to [GH #7](https://github.com/Escoto/EscotoDataFramework/issues/7) |
| ~~29~~ | ~~Wheel forces a pandas 2 upgrade on DBR 15.4~~ | ~~`pandas>=2` is a runtime dependency, but DBR 15.4 ships 1.5.3, so every job cluster upgrades it at install although nothing uses pandas yet. `pyspark` and `delta-spark` are declared too, though the runtime provides them.~~ | ~~Low~~ | Moved to [GH #12](https://github.com/Escoto/EscotoDataFramework/issues/12) |
